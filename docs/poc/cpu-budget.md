# 只有 CPU 也能跑：一个字形的预算表

结论先说：**能，但前提是"一个字一次前向"，而不是"一个字几十步去噪"。** 扩散模型在 CPU 上不是慢一点，是慢两个数量级。

## 实测基线（本仓库现状）

`hwpdf synth bench` 直接量一个字形从"引擎生成"到"矢量化成字"的耗时，不做外推假设。

```bash
hwpdf synth bench --style hw/font.ttf -n 64          # 解析式基线 stylefit
hwpdf synth bench --engine stub -n 64                # 下界参考
```

本机（Apple M4，10 核，单线程路径）实测：

| 阶段 | stylefit | 说明 |
|---|---|---|
| 引擎生成 | 0.54 ms/字 | 量倾角/笔宽 + 仿射 |
| 矢量化 + TTF | 1.36 ms/字 | 追踪轮廓、组装 glyf |
| **合计** | **1.9 ms/字** | 1000 字 ≈ 1.9 s，3755 字 ≈ 7 s |

在 2019 年的四核笔记本上这组数字大约慢 3–5 倍，仍然是"整本书几秒钟"的量级。

## 换成学出来的模型，怎么估

模型的成本几乎完全由"每个字形要跑多少计算"决定。按 64×64 输出、深度可分离卷积的小型生成器估算（约 200 MFLOP/字）：

| 机型 | 有效算力（卷积） | 200 MFLOP/字 | 1000 字 | 3755 字 |
|---|---|---|---|---|
| 四核轻薄本（AVX2） | 30–50 GFLOP/s | 4–7 ms | 4–7 s | 15–25 s |
| M4 / 现代六核 | 150–400 GFLOP/s | 0.5–1.5 ms | 1 s | 3 s |

int8 动态量化在 CPU 上通常再快 2–4 倍（精度损失对"再矢量化"这一步几乎不可见，因为最终是重新描轮廓）。

## 对照：扩散模型为什么不能这么算

FontDiffuser / Diff-Font 这类模型，一个字要 20–50 步去噪，每步是一个 1–5 GFLOP 的 UNet：

- 每字 ≈ 20–250 GFLOP，是上面小生成器的 **100–1000 倍**；
- 3755 个字 = 数十分钟到数小时，且显存/内存占用高。

所以它们适合做**离线教师**：在有机器的环境里跑一遍，蒸馏出小模型，或者直接产出训练数据。用户机器上不该跑。

## 让 CPU 路线成立的四条设计约束

1. **一次前向出整字**。不做迭代采样、不做自回归笔画。
2. **风格编码一次，解码多次**。10–50 个样本过一遍编码器得到 style 向量（几百 MFLOP，一次性），之后每个字只跑解码器。
3. **按需生成 + 磁盘缓存**。一篇文章通常只有 700–1500 个不重复字，不是 3755 个。`synth extend` / `render --grow` 已经是这个模式，缓存命中的字是 0.4 ms。
4. **输出分辨率可以低**。64×64 的灰度图足够——后面还要矢量化成贝塞尔曲线，笔画边缘的细节由拟合决定，不由像素决定。

## 现在已经能做到的

- `stylefit` 全程纯 CPU、无模型、无下载，整库 7 s；
- `synth bench` 可以把任何新引擎的成本量出来，不用凭感觉；
- 接入面 `--engine external --provider` 已就绪，小模型导出 ONNX 后按这个接口接进来即可。

真正的阻塞不是 CPU，是**权重许可**：候选模型除 zi2zi（Apache-2.0）外许可证空白，只能本地实验、不能分发。这也是为什么当前的默认路径不依赖任何模型权重。
